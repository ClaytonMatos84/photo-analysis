# ADR-003: Shared `AnalysisEmptyState` component with per-page content files and prop-driven visibility

## Status

Accepted

## Date

2026-07-21

## Context

ADR-001 and ADR-002 (PRD-level) decided that the photo, ad, and video analysis pages need a reusable pre-analysis empty state (3-step timeline + 4 benefit `Card`s), visible per page-specific rules, and that the photo page's image preview should move to render only alongside the result. This ADR covers the concrete technical shape: how the shared component is structured, where its per-page content lives, how visibility is computed in each view, and how styling/theming is wired.

The codebase already establishes conventions this design must follow: `<script setup lang="ts">` everywhere, PrimeVue components imported directly (`import X from 'primevue/x'`), scoped CSS per component, `*Types.ts` files for domain types, and the `v-animateonscroll` directive registered globally in `main.ts` for scroll-in entrance animations. `PageHero.vue` establishes a `--hero-accent` CSS custom property pattern for per-page accent color, though none of the three views currently override the default (`#357ae8`).

## Decision

**Component boundary**: add one new component, `src/components/utils/AnalysisEmptyState.vue`, generic and content-agnostic. It accepts:

```ts
export interface AnalysisEmptyStateStep {
    number: number
    title: string
    description: string
    icon?: string
}

export interface AnalysisEmptyStateBenefit {
    icon: string // PrimeIcons class, e.g. 'pi pi-images'
    title: string
    description: string
}

interface Props {
    steps: AnalysisEmptyStateStep[]
    benefits: AnalysisEmptyStateBenefit[]
    accentColor?: string // defaults to the same '#357ae8' PageHero already defaults to
}
```

Internally it delegates step rendering to the pre-existing `StepsSection`/`StepCard` components (extracted from `HomeHowItWorks.vue` as part of this feature, and reused as-is by the refactored home page) — not PrimeVue `Timeline` — followed by a responsive CSS grid of PrimeVue `Card`s for `benefits`, each showing its `icon` (rendered as `<i :class="icon" />`), `title`, and `description`. `StepsSection` renders each step as a `StepCard` (`Avatar` + numbered circle + title/description), laid out in a column on narrow viewports and a row with connecting arrows on desktop (`isDesktop` computed from a `window.resize` listener with proper `onUnmounted` cleanup) — no PrimeVue `Timeline` dependency is introduced. `AnalysisEmptyState` passes `title="Passo a passo"` to `StepsSection`, overriding its own `"Como Funciona"` default so the step-timeline section carries a heading contextually accurate for the analysis pages, and renders its own local "Benefícios" heading (with a `pi pi-check-circle` icon) above the benefit-card grid. The root element carries `v-animateonscroll="{ enterClass: 'animate-slide-bottom' }"`, matching the convention already used for dashboards on these same pages. `accentColor` is applied the same way `PageHero` applies it — as a `--empty-state-accent` CSS custom property consumed by scoped styles for the card icon backgrounds, and forwarded to `StepsSection` as `accent-color` for its own `--step-card-accent` custom property.

**Content ownership**: each page's step/benefit copy lives in its own content file under a new `src/content/` directory, one file per page, each exporting typed constants:

- `src/content/photoEmptyState.ts` → `photoEmptyStateSteps: AnalysisEmptyStateStep[]`, `photoEmptyStateBenefits: AnalysisEmptyStateBenefit[]`
- `src/content/adEmptyState.ts` → `adEmptyStateSteps`, `adEmptyStateBenefits`
- `src/content/youtubeEmptyState.ts` → `youtubeEmptyStateSteps`, `youtubeEmptyStateBenefits`

Each file imports the two interfaces from `AnalysisEmptyState.vue` (re-exported from its `<script setup>` block) and hard-codes 3 steps and 4 benefits whose copy is written by hand from that page's actual result type fields (`PhotoAnalysisResult`, `AdAnalysisResult`, `YouTubeAnalysisResult`). This is static content, not derived at runtime from the TypeScript types — the types only inform what the content author writes.

**Visibility logic**: each view computes its own `showEmptyState` boolean with a `computed()`, per the page-specific rule already decided in ADR-002:

- `PhotoAnalysisView`: `showEmptyState = !analysisResult.value` (empty state visible until a result exists; the image preview and dashboard render together once `analysisResult` is set, per the changed `PhotoDisplay` gating described in ADR-002).
- `AdAnalysisView`: `showEmptyState = !isImageUrlValid.value && !analysisResult.value` — hidden as soon as the URL preview becomes valid, or once a result exists.
- `YouTubeAnalysisView`: `showEmptyState = !analysisResult.value` (no separate pre-result preview exists on this page today).

The component is rendered with `<AnalysisEmptyState v-if="showEmptyState" ... />` placed as the first child inside each page's existing `<main class="upload-main">`, before the conditional preview/dashboard blocks. No new prop or slot is added to `PageHero` — the empty state stays out of the hero and inside `<main>`, consistent with where dashboards already render.

## Alternatives Considered

### Alternative 1: Per-page wrapper components delegating to a shared base

- **Description**: Build `PhotoEmptyState.vue`, `AdEmptyState.vue`, `YouTubeEmptyState.vue`, each wrapping a shared base component and hard-coding their own content internally.
- **Pros**: Keeps content colocated with a dedicated component per page; no separate content-file convention needed.
- **Cons**: Triples the number of components for content that is otherwise pure data; harder to see all three pages' content side by side; inconsistent with the project's existing pattern of keeping components UI-focused and data separate.
- **Why rejected**: The user chose the single generic component with content passed via props.

### Alternative 2: Inline content literals in each View's `<script setup>`

- **Description**: Define the `steps`/`benefits` arrays directly inside `PhotoAnalysisView.vue`, `AdAnalysisView.vue`, `YouTubeAnalysisView.vue`.
- **Pros**: No new files or directory; fewer indirections.
- **Cons**: Bloats already-substantial view files with static copy; harder to review/update content without touching view logic.
- **Why rejected**: The user chose dedicated content files under a new `src/content/` directory for separation of concerns.

### Alternative 3: PrimeVue `Timeline` component

- **Description**: Use PrimeVue `Timeline` (vertical layout) to render the 3 steps, as originally decided.
- **Pros**: Built-in vertical/horizontal layout switching with no manual resize-listener code; matches the general "steps" semantic Timeline components are designed for.
- **Cons**: Introduces a second, visually distinct step-rendering pattern into the app alongside the home page's existing `Avatar` + numbered-circle pattern (`HomeHowItWorks.vue`), fragmenting the "how it works" visual language between the home page and the analysis pages.
- **Why rejected**: The team chose to factor `HomeHowItWorks.vue`'s existing step pattern into reusable `StepsSection`/`StepCard` components and reuse them both on the home page and inside `AnalysisEmptyState`, keeping one consistent step-timeline visual language across the whole app instead of introducing `Timeline` as a second pattern.

### Alternative 4: No heading above either the step timeline or the benefit-card grid

- **Description**: Suppress `StepsSection`'s `title` entirely (original decision) and add no heading above the benefit-card grid, so the empty state has no section labels at all.
- **Pros**: Slightly less visual clutter; no need to keep two ad-hoc headings styled consistently with each other.
- **Cons**: The two content blocks (flow vs. outcomes) are not labeled, which was found to reduce scannability of the empty state during review.
- **Why rejected**: Revised, user-approved decision — the empty state now carries a "Passo a passo" heading (via `StepsSection`'s `title` prop) and a "Benefícios" heading (local markup with a `pi pi-check-circle` icon) to clearly label each block.

## Consequences

### Positive

- One small, focused, reusable component covers all three pages; content changes never touch component logic.
- Content files are trivially readable and reviewable independent of Vue/PrimeVue knowledge.
- Reusing `StepsSection`/`StepCard` keeps one consistent step-timeline visual language between the home page and the three analysis pages, instead of introducing a second, visually distinct pattern via `Timeline`.
- `accentColor` prop keeps the door open for future per-page color differentiation without any structural change.

### Negative

- Introduces a new top-level `src/content/` directory and a new `*EmptyState.ts` naming pattern not previously used in the project (existing convention only had `*Types.ts`, `*Service.ts`, `use*.ts`).
- Static content duplicates knowledge already present in the result-type interfaces; if a result type's fields change materially, the content files must be updated by hand (no compiler-enforced link beyond the shared step/benefit shape).

### Risks

- Content/type drift over time (see ADR-001's equivalent risk). Mitigation: content files import the interfaces from `AnalysisEmptyState.vue`, so at minimum the shape (not the semantic accuracy) is type-checked; semantic accuracy is a manual-review responsibility documented in `_tests.md`.

## Implementation Notes

- `AnalysisEmptyState.vue` and its two exported interfaces are the only new files touching `src/components/utils/` directly; `StepsSection.vue`/`StepCard.vue` are also new files under `src/components/utils/`, extracted from `HomeHowItWorks.vue` and reused by both `AnalysisEmptyState` and the refactored `HomeView`. `src/content/` is a new directory with exactly 3 new files.
- `StepsSection` renders its own `title` heading (`<h2>`, defaulting to `"Como Funciona"` on the home page); `AnalysisEmptyState` overrides it with `title="Passo a passo"` (a revised, user-approved decision — the original design suppressed this heading entirely, see "Alternative 4" below) and adds its own local "Benefícios" heading (with a `pi pi-check-circle` icon) above the benefit-card grid, so both content blocks inside the empty state are clearly labeled.
- `PhotoAnalysisView.vue` changes its `PhotoDisplay` render condition from `v-if="imageFile"` to `v-if="imageFile && analysisResult"` (rendered alongside `PhotoAnalysisDashboard`, not gated by `imageFile` alone).
- No changes to `PageHero.vue`, any service, any store, or any API contract.
