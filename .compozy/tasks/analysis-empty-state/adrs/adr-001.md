# ADR-001: Reusable pre-analysis empty state with a step timeline + benefit cards

## Status

Accepted

## Date

2026-07-21

## Context

The photo, ad, and video analysis pages (`PhotoAnalysisView`, `AdAnalysisView`, `YouTubeAnalysisView`) share the same layout: `MainLayout` → `PageHero` (title, icon, description, submission form) → a `<main>` region that only renders content after an analysis result exists. Before the first submission, that `<main>` region is empty, leaving a large blank area below the hero. This hurts first impressions and gives the user no sense of what the feature does or what they will receive.

The three pages already share structure and CSS class names (`upload-main`, `analysis-loading`, animation classes), and `PageHero` already establishes a per-page accent color (`--hero-accent`) and scroll-in animation pattern (`v-animateonscroll`). PrimeVue 4 has no built-in "empty state" component. `HomeHowItWorks.vue` already implements the numbered-step visual pattern this feature needs (`Avatar` + numbered circle + title/description, collapsing to a single column on mobile); PrimeVue ships `Card`, which maps naturally onto "what you'll get" content.

## Decision

Introduce one reusable component, `AnalysisEmptyState.vue` (in `src/components/utils/`), rendered inside the `<main>` region of all three pages whenever there is no result yet and no other preview content is showing. It combines:

- A step timeline, built on the pre-existing `StepsSection`/`StepCard` components (extracted from `HomeHowItWorks.vue`), with exactly 3 numbered steps describing how the analysis flow works for that page (submit → wait → view result).
- A grid of exactly 4 PrimeVue `Card` items below the timeline, each describing one field/insight the analysis response will return, using a plain-language explanation of what that field means (not just the technical field name).

Each page passes its own step and benefit content as props/config, sourced from that page's actual result type (`PhotoAnalysisResult`, `AdAnalysisResult`, `YouTubeAnalysisResult`) so the copy accurately previews what the user will receive. The component reuses the page's accent color for visual consistency with `PageHero` and applies the same scroll-in animation convention already used across these views.

The empty state remains visible during the loading/analyzing phase (behind or above the spinner) and is hidden as soon as any preview or result content would otherwise occupy that space, per page-specific rules (see ADR-002 for the photo page's preview timing change).

## Alternatives Considered

### Alternative 1: Page-specific bespoke empty states (no shared component)

- **Description**: Build a different empty-state layout per page, tailored independently.
- **Pros**: Maximum per-page creative freedom.
- **Cons**: Triples the implementation and maintenance effort; risks visual inconsistency across the three otherwise-identical page shells.
- **Why rejected**: The user explicitly asked for one consistent empty state reused across all three pages, only varying the textual content.

### Alternative 2: Static decorative-only empty state (illustration + generic text, no timeline/cards)

- **Description**: Show a single icon/illustration with a friendly headline and one line of text, no structured content.
- **Pros**: Fastest to build.
- **Cons**: Misses the chance to educate the user about the flow and the value of the analysis; does not use the "steps + benefits" content the user asked for.
- **Why rejected**: The user asked for both a "how it works" explanation and a preview of the benefits/insights returned, which requires structured content, not a single decorative message.

## Consequences

### Positive

- The large blank area below the hero on all three pages is replaced with informative, on-brand content.
- Users understand the flow and the expected output before submitting, which can increase trust and completion rates.
- One shared component keeps the three pages visually consistent and easy to maintain.

### Negative

- Adds a new shared component and per-page content config that must be kept in sync if the result types change.
- Reuses the pre-existing `StepsSection`/`StepCard` components (extracted from `HomeHowItWorks.vue`) rather than a new PrimeVue `Timeline`, so no bundle-size increase from a previously-unused PrimeVue component.

### Risks

- Content can drift out of sync with the actual API response shape over time. Mitigation: keep the benefit-card copy tied to the field names of the existing result types and update it whenever those types change.
